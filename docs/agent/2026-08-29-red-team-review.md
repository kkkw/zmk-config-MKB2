# 既存コードのレッドチームレビュー

レビュー日: 2026-08-29
対象: `HEAD` (`b8ad339`) から `origin/main` (`530ad68`) までのフォーク固有差分と、現在の左ENCビルド構成

利用者からの実機観測: Bluetooth接続ではキーを押してから反応するまで少し鈍く感じ、意図しない連続入力も発生している。有線接続での比較確認は継続中で、連続入力が通常キーかエンコーダーかは未確定。

## レッドチームの役割

このレビューでは、実装者の意図を補強するのではなく、現在の設定が利用者の症状を発生させる経路を探す。指摘はコード上の事実、症状との対応、反証する試験を分ける。実機で確認できない事項は解決済みと扱わない。

## 指摘

### 1. Bluetooth遅延と連続入力の原因が未分離

現在の `MKB_L_Base.conf` はBluetoothとsplit centralを有効にし、接続間隔のperipheral側希望値を15msにしている（`CONFIG_BT_PERIPHERAL_PREF_MIN_INT/MAX_INT=12`）。これは遅延の候補だが、central側やsplit側の実際の交渉結果をこのリポジトリだけでは確認できない。

また、現在のファームウェアにはUSBログ出力設定があるものの、今回の入力症状を自動判定するテストやログ採取手順はない。Bluetoothだけで再現するか、有線でも再現するかを先に固定しない限り、接続設定とスキャン設定を同時に変えるのは危険である。

判定: 高。まず有線/Bluetooth比較を行う。

### 2. `&mt` の設定は一部キーの反応を遅く見せる可能性がある

`config/MKB.keymap:16-20` で、mod-tap全体に `tapping-term-ms = <280>`、`quick-tap-ms = <175>`、`require-prior-idle-ms = <150>` を設定している。通常の単純な `&kp` には適用されないが、TAB、QMARK、MINUS、LANG1などのmod-tapキーでは、短押しと修飾キー押下の判定待ちが発生し得る。

「特定のキーだけ鈍い」なら有力だが、「すべてのキーが鈍い」ならこの設定だけでは説明できない。

判定: 中。mod-tapキーと単純な`&kp`を同じBluetooth接続で比較する。

### 3. EC11はキースキャン用デバウンスの対象外である可能性がある

`MKB_L_ENC.overlay:2-4` でEC11のGPIOと `steps = <24>` を定義し、`MKB_L_ENC.overlay:8-10` で1回転あたり10回のsensor triggerを設定している。キー用の `CONFIG_ZMK_KSCAN_DEBOUNCE_PRESS_MS/RELEASE_MS` は、EC11のsensor driverのチャタリングを直接抑える設定とは限らない。

「意図せず連続」がエンコーダーのスクロールなら、物理チャタリング、1ノッチあたりのtrigger数、またはsensor-rotateのqueueのどれかを切り分ける必要がある。現在の `tap-ms = <24>` はqueue滞留を減らす候補だが、実機で連続出力がないことはまだ証明していない。

判定: 高。ただし対象が通常キーならこの指摘は適用しない。

### 4. 通常キーの連続入力は、ファームウェア以外の要因も残っている

通常キーでBluetooth時だけ連続入力し、有線では発生しない場合、キーリリースイベントの遅延・欠落、split通信、ホスト側のキーリピートが候補になる。有線でも同じキーだけが連続する場合は、物理スイッチ、基板、GPIO入力、またはキースキャンのチャタリングを優先する。

現在のデバウンス値はpress 5ms、release 7msであり、購入者の実機個体に対して十分かはコードだけでは断定できない。数値変更を先に行うと、Bluetooth由来の問題と物理由来の問題が混ざる。

判定: 高。症状の接続方式とキー名を記録するまで設定を変更しない。

### 5. 書き込みスクリプトの終了コードは、実機反映と一致しないことがある

`scripts/flash-uf2-macos.sh:153` はUF2コピー直後にデバイスが再起動・アンマウントすると、macOSの `cp` が `Device not configured` で終了する場合がある。今回もこの挙動が発生したが、利用者は実機への反映を確認した。

したがって、スクリプトの終了コードだけで「書き込み失敗」と判断してはいけない。一方、現行スクリプトには、UF2ドライブの消失を正常完了の証拠として記録する処理や、再起動後のファームウェアバージョン確認処理はない。

判定: 中。運用上の既知事象として扱い、書き込み後の実機確認を必須にする。

## 反証試験

1. Bluetoothを切り、有線USBだけで単純な`&kp`を10回短く押す。
2. 同じ有線状態で、mod-tapキーと単純な`&kp`を比較する。
3. Bluetoothで右トラックボールに触れず、左側の通常キーだけを試す。
4. エンコーダーを上下に1ノッチずつゆっくり10回操作し、スクロールが1ノッチにつき1回か、複数回か、回り続けるかを記録する。
5. 有線とBluetoothで、同じキー・同じエンコーダー操作を比較する。

## 変更の停止条件

- 有線でも通常キーが連続入力する場合: Bluetooth設定を変更せず、物理スイッチ、GPIO、kscanデバウンスを個別に調べる。
- Bluetooth時だけ通常キーが連続入力する場合: エンコーダー設定を変更せず、BLE/splitの接続状態とイベント経路を調べる。
- エンコーダーだけが連続する場合: `steps`、`triggers-per-rotation`、`tap-ms`、センサーの物理チャタリングを一つずつ比較する。
- すべてのキーが遅い場合: `&mt` の値だけを変更しても解決しない可能性が高い。接続間隔とsplit通信を別試験にする。

## レビュー結論

現時点で最も危険なのは、Bluetooth、キーのデバウンス、EC11のtrigger数を同時に変更してしまうことである。現在の候補UF2は、左エンコーダーの通常解像度出力を確認するためのものとして保持し、次のファームウェア変更は上記の反証試験で症状の経路を確定してから行う。
